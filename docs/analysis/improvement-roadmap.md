### 결함 1 — 길이 빗살처럼 남았다가 마지막에 채워진다

**원인은 하나가 아니라 셋이다.**

| # | 원인 | 실측 |
|---|---|---|
| A | `_spread`(`one_stroke_bake.dart:367`)가 8-이웃 **홉 수** BFS라 소유권이 체비쇼프 거리로 갈린다. 뼈대 순회는 대각을 1.4142로 세는데 전파만 1.0으로 센다 — 한 파이프라인에 거리 정의가 둘 | 고립 구멍 최악 **16~79개**/지도 |
| B | `_oneStrokeOrder`의 DFS가 되짚다 마지막에 닿는 몇 픽셀에 최댓값을 준다 | map_basic_01에서 3픽셀 |
| C | `bakeOneStrokeOrder:89`의 `field[i] < 0 ? 254` — 열림 연산에 뼈대가 지워진 조각을 **전부 맨 끝**에 몬다 | 길 마스크 덩어리 54~144개 중 뼈대 있는 것은 **언제나 1개**. 나머지가 길 픽셀의 **2.3~17.7%**, 최대 덩어리 **203px** |

사용자가 말한 "마지막에 채워진다"는 A보다 **C가 더 크게 기여한다**. `map_basic_03`은 화면 맨 위 200px 가로줄의 절반이 연출 맨 끝에 통째로 팝한다.

**수정 방향**

- **A → 손수 짠 이진 힙 다익스트라**(8-이웃 대각 1.4142 측지 거리의 정확해). 작업본의 **체임퍼 2-패스는 기각**한다. 근거 셋:
  - 안 멎는다. 패스 상한 8→16→64→**256**에서도 10종 전부 `changed`가 참이다. `dist`가 `Float32List`인데 `dist[j]+cost`를 float64로 계산해 float32로 되쓰는 왕복에서 매 패스 1 ULP씩 깎인다. 상한 8은 보험이 아니라 **항상 발동되는 조기 중단**이다.
  - 그래서 정확해 대비 최대 **64px**을 못 닿은 채 남긴다 → 254로 떨어져 맨 끝에 팝한다. **고치려던 증상을 새로 만든다.**
  - 마스크가 캔버스의 1.7~6.9%인데 `w*h`를 16번 훑어 **2배 느리다**: 체임퍼 평균 4.04 ms vs 힙 다익스트라 **2.07 ms**(BFS 0.63 ms).
  - 힙 키를 `Float32List`로 두는 것이 중요하다 — `dist`와 정밀도가 같아야 `pop` 순서와 비교가 어긋나지 않는다. 체임퍼가 안 멎던 원인이 정확히 이 불일치다.
- **C → `_adoptIslands`**: 뼈대에 못 닿은 조각을 연결요소로 묶어 `reach=16` 안의 가장 가까운 순서값을 **통째로** 물려준다. 조각 안에서 다시 진행도를 나누지 않는다 — 뼈대도 없는 것이 제 순서를 갖는 척하게 된다.
- **B → 안 건드린다.** 뼈대 덩어리가 언제나 1개라 `_traversalStarts` 정렬로는 안 고쳐지고, 고치려면 오일러 경로 자체를 손대야 한다. A를 고치면 이 세 점의 소유권이 얇은 대각선에서 지름 4~6px 뭉친 덩어리로 바뀌어 고립 구멍 지표로는 0~6이다. `_oneStrokeOrder` 문서에 한 줄만 남긴다.

**효과와 비용**

| | 얻는 것 | 비용 |
|---|---|---|
| A | 고립 구멍 16~79 → **0~6** | bake +1.4 ms |
| C | 맨 끝(254) 픽셀 208~399 → **8~146**(평균 −76%) | +0.36 ms |

합쳐 bake 19.12 → 약 20.5 ms(+7%), prepare 29.22 → 약 30.6 ms. 840px은 87.21 → 약 95 ms(외삽). **난이도 S · 위험 low**(힙 버그가 조용하다는 점만 medium).

**잠금 테스트** — `test/plan/spread_comb_test.dart` (신규, 자산 0, 공개 CI에서 늘 돈다)

- 합성 **머리핀**·**뱀꼴** 4케이스에서 "8-이웃 중 6개 이상이 드러났는데 자기는 아직"인 길 픽셀 수의 최댓값이 0.
- 곧은 막대로는 안 나온다(대각 굵기 15에서도 0개). 시각이 크게 다른 두 획이 **이웃해야** 소유권 경계가 생긴다. 실측: 홉 수 BFS 4~8개, 측지 다익스트라 0.
- 커버리지 테스트로는 못 잡는다 — 빗살 픽셀도 결국 드러나므로 진행도 1에서는 100%다. **중간 프레임**을 봐야 한다.

### 결함 2 — X 교차부가 잘록하다

**원인 한 줄**: `cross_stroke_detector.dart:179`의 `toBackslash <= toSlash`가 두 축의 **각 이등분선**이라 교차부가 사분면으로 갈린다. `_normalDistance`가 나누는 `halfWidth`는 두 축이 같은 `band` 값이라 비교에서 상쇄된다 — '정규화'라는 안전장치는 실제로 존재하지 않는다.

**실측 허리비**(축방향 20칸 중 가운데 2칸 ÷ 양옆 4칸. 1.0이면 교차부에서 폭이 안 변한다. 기하학적 이상값은 `1/sinθ`, 정본 사잇각 83~99° → **1.00~1.15**)

| | `\`/`/` 픽셀 | 허리비 범위 |
|---|---|---|
| HEAD (이등분선) | 555~566 / 494~507 | **0.20~0.32** ← 사용자가 본 잘록 |
| 작업본 (두 띠 교집합) | 680~779 / 281~390 | **1.70~2.25** ← 반대로 부푼다 |
| **제안 (`\` 띠 소속, 0.5)** | 560~635 / 427~510 | **0.85~1.14** |

작업본이 부푸는 이유: `halfWidth`에 들어 있는 값이 실제로는 스윕 창의 **전체 폭**(`:277`의 `halfWidth: band`)이라 `<= 1`은 축에서 ±획 굵기 전체를 뜻한다. 그 띠 둘의 교집합은 진짜 교차 마름모의 2배여서 `/` 팔의 뿌리까지 삼킨다.

**수정 방향**: `\` 띠 소속만 본다 — `toBackslash <= 0.5`면 `\`, 둘 다 밖이면 가까운 축(버리지 않는다). `_ownBandHalf = 0.5` 상수로 두고 "`halfWidth`가 전체 폭이라 실제 반폭은 절반"을 그 자리에 적는다. 이름을 고치는 게 맞지만 그러면 python 굽기 도구와 필드명이 갈린다.

**`within`에 미치는 영향**

- 안 바뀌는 것: 두 획 모두 양 끝 팔이 남아 축방향 `extent` 불변 → `slashLength`/`backslashLength`/`measure` 그대로. 애초에 **X 타이밍은 `measure`를 안 쓴다**(`timing_policy.dart:143` 고정 220 ms). 총 재생 2251 ms 불변.
- 바뀌는 것: `/`가 가운데를 내주므로 "죽은 구간"이 생긴다. 축방향 20칸 중 빈 칸 — HEAD 0/20, **작업본 8~9/20(220 ms 중 88~99 ms)**, 제안 3/20(33 ms). 작업본은 `/` 재생의 40~45% 동안 펜이 멈춘 것처럼 보인다. 제안의 15%는 선단 폭(10.6코드 ≈ 이 창에서 9 ms)에 거의 묻힌다.
- `_fillWithin`을 "축 투영" 대신 "배정 픽셀 순위"로 바꾸면 죽은 구간이 0이 되지만 **기각**한다 — 펜이 교차부에서 순간이동한다. 진짜 펜은 이미 그은 자리를 같은 속도로 지나간다. **죽은 구간 15%는 올바른 물리다.**
- 방어 한 줄 추가: `backslashLength <= 0 || slashLength <= 0`이면 `null` 반환(X 판정 포기 → 문구로 강등, 이미 정의된 안전 경로).

**난이도 S · 위험 medium**(레포 밖 작업이 딸려 온다).

**잠금 테스트** — `cross_stroke_detector_test.dart`에 허리비 시험 추가. 합성 X 7케이스(굵기 8/14/22, 회전 −30~25°)에서 `inInclusiveRange(0.75, 1.45)`. **HEAD에도 작업본에도 빨간불, 제안에만 초록.** 상한과 하한을 둘 다 잡으므로 누가 `_sweep`에서 `halfWidth: band`를 `band/2`로 "고쳐서" 상수가 2배 틀려도 잡힌다.

**⚠️ 선행 조건 — 이 변경을 지킬 그물이 레포에 없다.** `cross_stroke_corpus_test.dart:181-182`가 `backslashCount`를 정확히 못 박지만 픽스처 `fixtures/cross_expected.json`도, 굽기 도구 `tool/bake_cross_calibration.py`도 레포에 없다(`find . -name "bake_cross_calibration*"` → 0건). `_fixtureSkip`이 항상 켜져 **이 그룹이 한 번도 안 돈다.** 즉 로컬·공개 CI는 초록이고 픽스처를 가진 사람만 빨개진다. 파일 머리 `:17`이 "python과 한 글자도 어긋나면 안 된다"고 못 박은 쌍둥이가 **이미 부재중**이다. PR에 명시할 것: ⓐ python 사본 동일 수정 ⓑ 픽스처 재굽기 ⓒ `cross_calibration.g.dart` 실측 요약 주석 갱신 — **셋 다 이 레포 밖**이다.

### 결함 3 — "발견한곳"이 음절이 아니라 연결요소 6덩어리

**원인 한 줄**: `annotation_segmenter.dart:82`가 순수 8-이웃 연결요소라, '발'의 받침은 따로 떨어지고(과분할) '견한'은 래스터에서 실제로 붙어 있다(과병합) — **규칙 하나로 둘 다 못 고친다.**

**codex 권고 평가 — 동의한다. 386 ms 계산까지 맞다.**

| 안 | 세그먼트 | 글씨 구간 | 총 재생 |
|---|---:|---:|---:|
| 현재(연결요소 6) | 6 | 944 ms | 2251 ms |
| **음절 4** | 4 | **670 ms** | **1977 ms** |
| 자모 12 | 12 | 1330 ms | 2637 ms |

자모 12개는 `12×70 + 11×30 = 1170 ms`(전부 70 ms 하한에 걸린다) vs 현재 784 ms → **+386 ms**. codex가 말하지 않은 **더 센 두 번째 이유**: `k=24`의 선단 폭이 10.6코드 = 시간축 4.2%인데, 자모 12개면 창 하나가 70/2637 = **2.7%**라 **선단보다 짧다** — 다음 자모가 미리 비친다. `sharpness.dart:62`가 자기 입으로 "덩어리 10개 넘으면 k를 128로"라 적었지만 k는 굽는 쪽과 그리는 쪽이 공유하는 **표현 계약**이라 모든 지도의 선단이 같이 변한다. 음절 4개(창 ≈ 5.4%)는 이 문제를 아예 안 만든다.

**힌트 없이 가능한가 — 부분적으로만.**

경계는 래스터에 남아 있다. `map_basic_01` 문구(x 156~261)의 열 투영에 골짜기가 x=187·210·238에 있고 음절 폭 31/24/27/24로 거의 균등하다. 하지만 **몇 개로 자를지**는 못 정한다 — '견한'은 8-이웃으로 이어진 한 덩어리(51×36px)라 연결성으로 못 가르고, '곳'은 세 덩어리로 떨어지며 그중 첫 조각이 '한'과 가로로 2px 겹친다. 가로 겹침 병합만 돌리면 **"발견한곳"이 2덩어리(폭 31/74)로 뭉친다** — 중앙값 피치 추정이 여기서 무너진다. 게다가 계약상 글씨가 아닐 수도 있다(`map_deep_05`는 육각형 얼굴 그림). **결론: 힌트를 받는다. 기본 `null`(현행 유지), 아는 호출부만 준다.**

**API — 작업본의 `AnnotationSegmenterConfig.expectedSyllableCount`가 옳은 자리다.** `RevealDetectConfig.annotation`으로 이미 흐르므로 `RevealPreparer` API 변경이 없고, `const`로 `compute` 경계를 넘고, `purity_test`의 `duration|millis|_ms` 정규식에 안 걸린다. 보완: 정본에 2줄짜리가 있으므로(`map_basic_02`, 11덩어리) "**줄 하나에 몇 자인가**"임을 문서에 못 박고 `List<int>?`로 넓힐 여지를 남길 것.

**작업본을 정본에 돌린 결과 — 음절 나누기는 잘 되고, 순서에 버그가 하나 있다.**

`expectedSyllableCount: 4` → 덩어리 6 → **4**, 음절 bbox 폭 31/23/27/24(정확히 발|견|한|곳), 총 재생 2251 → **1977 ms**. 그런데 음절 안 `within`이 무엇을 따라 커지는지 재면:

| 음절 | corr(within, x) | corr(within, y) |
|---|---:|---:|
| **발** | **1.00** | 0.31 |
| 견 | 0.56 | 0.77 |
| 한 | 0.69 | 0.27 |
| 곳 | 0.57 | 0.91 |

세 지도 모두 첫 음절이 **완전한 좌→우 wipe**다(map_deep_01 0.99, map_deep_02 0.97). 원인은 `_jamoProgress`의 ① `if (strokes.length < 2) return null` — '발'(ㅂㅏㄹ)은 래스터에서 한 덩어리(567px)라 기본 좌→오 wipe로 떨어진다. ② 자모 안이 x만 본다.

**수정 방향**: `_jamoProgress`를 **행 우선 순위**(y가 1차 키, x가 2차 키)로 바꾸고 한 조각 예외를 제거한다. `local = (row*span + column) / last`, 바깥 키는 여전히 자모 rank. 사용자 지정("각 음절 안에서 위→아래, 같은 높이는 좌→우")을 글자 그대로 옮긴 것이고, 자모를 못 갈라도 규칙이 안 무너진다. **난이도 S · 위험 low.**

- 검토 후 기각: 음절 전체를 통짜 행 우선(= `strokes` 무시)은 API 3개를 지울 수 있지만 ㅂ과 ㅏ가 같이 자라 글씨 쓰는 느낌이 준다 — 되돌리기 싸니 실기 A/B 값어치는 있다. 자모마다 세그먼트는 +660 ms + 선단 문제로 기각. 힌트 자동 추정은 위 2덩어리 실측으로 기각.

**잠금 테스트**: 합성 문구(두 번째·세 번째가 1px 다리로 이어진 네 글자꼴)로 ① 힌트 4 → 세그먼트 4, 각 세그먼트 안에서 (y,x) 사전순 대비 `within` 뒤집힘이 자모 수 미만 ② **힌트 없으면 4보다 많다**(자동 추정 금지를 잠근다). 실지도 문구를 픽스처로 넣으면 `.gitignore` §디자인 자산에 걸린다.

**타이밍 실측표**는 힌트를 준 화면에서만 바뀐다(2251 → 1977 ms, −12%). `RevealStageMarks` 경계값도 바뀐다(길 0.3096 → 0.352) — `stage_marks_test.dart`가 리터럴을 들고 있으면 갱신.

### 파고들 가치가 있는 것

#### ② 재현성은 성능으로 사기 좋은 자리다

커널 민감도를 실측했다(879×1065 → 347×420, PIL로 커널만 교체, 임계 18/200/35 동일).

- 길 마스크 픽셀: box 2368 ↔ mip2 2610(**+10.2%**). 커널 간 IoU **0.816~0.969** — 길 픽셀의 3~18%가 커널 따라 갈린다.
- **mip2가 언제나 box에서 가장 멀다**(IoU 0.816~0.933). `FilterQuality.medium`이 바로 밉맵 경로이고, 밉 체인을 어떻게 만드느냐가 백엔드마다 갈리는 지점이다. 879→347은 2.53배라 밉 레벨 1과 2 **사이**에 걸려 두 레벨 lerp로 떨어진다 — 최악의 자리.

**그런데 형태정리가 대부분을 흡수한다.** 닫힘×2·열림×2 뒤 Zhang-Suen 뼈대 픽셀 수로:

- 긴 길(deep_02~06·special_01, 600~790px): 커널 간 **±1~2%**. 안정.
- **짧은 길(basic_01~03, 120~165px): −10.4% ~ +8.6%.** `map_basic_03`은 bilinear 120 ↔ mip2 139로 **15.8% 폭**.

하필 `map_basic_03`이 `length_profile.dart:30`의 하한(124.5)을 정하는 지도다. **리샘플러가 결과를 흔드는 게 아니라 자 자체를 흔든다.** 641 vs 697의 8.7%가 이 폭 안에 정확히 들어오고, `preparer_corpus_test.dart:72`의 `closeTo(2251, 120)` = ±5.3%는 이미 그보다 좁다 — **테스트를 빨갛게 만들 크기다.**

비용 여유는 넉넉하다: @420에서 `rgbaAt ×2` 5.67/29.22 = **19.4%**, @840에서 12.25/118.52 = 10.3%. 회귀선으로 장당 대략 0.5 ms 고정 + 9.7 ns/출력픽셀. ②를 3배 비싸게 만들어도 전체는 40%만 는다.

**권하는 조합**: 프리베이크(2안-3)를 먼저 하고, 그 위에 순수 Dart 리샘플(2안-1)이나 원본 해상도 굽기(2안-2)를 얹는다. 프리베이크가 후자의 비용을 빌드 머신으로 옮기기 때문이다. 다만 프리베이크와 런타임 굽기가 **다른 리샘플러로 나오면 같은 앱에 두 종류의 연출이 섞이므로**, 순수 Dart화가 프리베이크의 짝이다.

#### ④-1 잘못된 통념이 6개월을 잡아먹었다

형태정리 시간이 마스크 크기와 무관하게 8.88~9.14로 거의 일정하다 — 길이 2,254~10,023px로 4.4배 차이나는데도. 원인은 알고리즘이 아니라 훑는 범위다. `_dilate`가 **배경 픽셀마다** 8-이웃을 뒤지는데 길은 캔버스의 1.7~6.9%라 98%가 낭비고, 그걸 4번 돌린다. `_erode`는 이미 전경만 본다.

이 세 최적화(−11.9 ms)가 **결함 1의 +1.76 ms를 완전히 흡수한다.** ④-2 평활(+0.55)까지 넣어도 bake는 16.06 → 약 4.7 ms다. 즉 **결함 1·④-1·④-2를 묶으면 정확도를 올리면서 굽기가 3배 이상 빨라진다.** 셋 다 난이도 S다.

#### ⑧ 부족한 건 비트가 아니라 배분이다

길은 76코드 × 2,505px = 코드당 33px이라 1코드 계단이 선단(≈350px 램프)의 1/10 — 양자화 밴딩은 안 보인다. 반대로 문구 덩어리는 5.7~12.1코드라 통째로 선단 안이다. **같은 텍스처에서 한쪽은 남고 한쪽은 모자란다.** 16비트로 올려도 선단이 65535/k로 같이 커져 비율이 그대로라 **하나도 안 풀린다.** 배분(time-warp)이 유일한 정공법이고, 그게 되면 ⑦의 예산 정책이 텍스처를 안 건드리게 된다.

다만 **난이도 L**이고 `stage_marks` 계약을 건드린다. 그 전 단계로 `annotationGap → 0`(S/low)과 음절 4개(결함 3)가 덩어리 수를 6~12에서 4로 줄여 압박을 상당히 덜어 준다 — **⑧은 그 둘 뒤에 다시 판단하라.**

#### ⑤-B 문서가 약속한 그물이 실제로 없다

⑤-A를 고쳐도, ⑥을 고쳐도, 이 레포 안에서 빨개지는 것이 하나도 없다. `_fixtureSkip`이 항상 켜져 있고 python 쌍둥이가 부재중이다. **⑤-A를 픽스처 복구보다 먼저 머지하면, 나중에 재구운 카운트가 새 규칙 기준인지 옛 규칙 기준인지 아무도 모른다.** 순서를 지켜야 한다.

#### ⑨ 측정 없이 셰이더로 가지 마라

이 레포는 굽기 29.22 ms를 실측해서 결론을 냈다. 렌더에도 같은 잣대를 대야 한다. "raster가 프레임 예산의 30% 이상"을 숫자로 보이기 전엔 saveLayer 2겹은 문제가 아니라 가정이다. 셰이더로 가면 **임계식이 GLSL로 복제되어** `RevealSharpness`가 k를 혼자 소유한다는 핵심 불변식이 깨지고, `purity_test`가 감시 못 하는 `.frag`에 두 번째 사본이 생긴다 — 그게 정확히 원본이 앓던 "마지막 획이 반투명하게 남는" 버그의 재발 경로다. 게다가 web 지원이 대상인데 fragment shader의 web 지원은 버전·백엔드에 따라 갈려 **두 경로를 다 유지**해야 한다.

## 안 건드리는 게 맞는 것

**측정으로 기각된 것**

- **④-3 이중 양자화(254 → 76).** 254 단계를 건너뛰고 field를 곧장 시간축에 보내도 빗살 지표가 **그대로다**(over 44→44, 16→16, 209→209). 실제 쓰이는 코드 가짓수도 73→73 / 75→77. 76인 까닭은 양자화가 아니라 **일정 배분**(길 창 31% × 상한 244)이다. 이 축의 문제는 ④-2이지 양자화가 아니다.
- **가중 Dijkstra로 `_spread` 교체(대각 1.4142로 이음매를 줄이려는 목적).** 10종 전부에서 10코드 초과 픽셀이 2~5배 **늘었다**(44→229, 16→169, 359→919). 거리를 정확히 재면 Voronoi 경계가 더 반듯하고 길어져 경계 픽셀만 늘 뿐, 점프 크기는 그대로다. 비용도 4배. *(결함 1의 힙 다익스트라는 목적이 다르다 — 그건 소유권 정합이고, 이건 이음매 제거다.)*
- **체임퍼 2-패스.** 미수렴 + 64px 손실 + 2배 느림. 위 결함 1 참조.
- **란초스.** 한 장 36.58 ms(AOT) — 면적평균의 4~5배. 그리고 더 정확하지도 않다: 뼈대 편차가 box 대비 **가장 크다**(+8.6% / +5.8% / +5.1%). 링잉 오버슈트가 임계 18 근처 픽셀을 더 만든다.
- **음절 수 자동 추정.** 가로 겹침 병합만 돌리면 "발견한곳"이 2덩어리(폭 31/74)로 뭉쳐 중앙값 피치 추정이 무너진다.
- **뼈대 꼬리(B) 수정.** 뼈대 덩어리가 언제나 1개라 정렬로 안 고쳐지고, A·C를 고치면 얇은 대각선이 지름 4~6px 덩어리로 바뀌어 지표상 0~6이다.

**층 경계를 무너뜨리는 것**

- **굽기가 전역 일정을 알게 해서 한 번만 양자화.** 이득이 0인 것을 위에서 측정했고, plan 층이 창의 시작·폭을 아는 순간 `purity_test`가 소스 수준에서 잠근 분리가 무너진다 — 같은 계획을 스플래시에선 느리게, 목록에선 빠르게 그릴 수 없게 된다.
- **적응형/데이터 의존 임계(오츠·퍼센타일).** 리샘플이 백엔드마다 다른데 픽셀 통계로 정해지는 임계를 얹으면 같은 자산이 기기마다 다른 계획을 낸다. 고정 임계는 재현성이 목적이고 여유도 충분하다(diff 10배, rg 25~45).
- **크기 검사를 `detectReveal`에 넣기.** 거기는 RGBA 길이만 본다 — 그게 맞다. "같은 구도인가"는 `ui.Image`를 아는 층만 답할 수 있다.
- **`SequentialReveal`에 검사 추가.** 굽기에서 걸러지면 렌더는 어긋난 입력을 못 만난다. 같은 단언이 두 층에 있으면 정본이 어딘지 모르게 된다.
- **빗살을 렌더 블러·색행렬로 덮기.** 구조 결함을 표현 계층으로 미는 것이고, `sharpness.dart:52`가 이미 경고한 함정에 바로 걸린다.
- **임계식을 `RevealSharpness` 밖에 다시 쓰기**(셰이더 포함). `purity_test:123-137`이 파일 단위로 잠근다. 원본이 상수를 두 곳에 뒀다가 "마지막 획이 반투명하게 남는" 버그를 앓았다.

**얻는 것보다 파장이 큰 것**

- **세선화를 거리변환 ridge로 교체.** 비용의 30%(4.77 ms)뿐이고 ④-1 뒤엔 1.5 ms다. 위상이 통째로 바뀌어 `_pruneSpurs`·`_traversalStarts`·길이 골든·커버리지 골든이 전부 재승인. **이득 1 ms에 위험 전부를 거는 거래.**
- **16비트 텍스처.** 메모리 추가 비용이 0이고 아핀도 유지되지만 **이 문제를 하나도 안 푼다**(선단이 같이 커진다). 게다가 translation 열이 ≈1.57e6이 되어 색행렬을 half-float로 도는 경로에서 fp16 최대 65504를 넘어 터진다.
- **마스크 두 장.** saveLayer가 2겹 → 4겹이 되어 ⑨의 유일한 프레임 비용이 배가 된다. 얻는 것은 X 교차부 하나뿐인데 그건 배정 규칙이 plan 층에서 공짜로 준다.
- **`FilterQuality`를 none/low로 못 박기.** none은 2.53배 축소에서 가는 길을 잃고, low는 `map_basic_03` 뼈대가 box 대비 −10.4% — 하필 하한을 정하는 지도에서 제일 틀어진다. 어느 값이든 **여전히 위임**이라 백엔드 동일성은 없다. 값을 바꿀 게 아니라 위임을 끊어야 한다.
- **`targetWidth`로 디코드에서 축소.** 디코드는 210/420/840 어디서나 5.87/5.71/5.75 ms로 **평평하다**(항상 원본을 푼다). 절반을 아껴도 prepare의 10%. 대가로 web에서 `createImageBitmap(resizeWidth:)` 경로가 열려 재현성 구멍이 브라우저 수만큼 늘어난다 — 목표와 정반대.
- **`kBakeLongSide`를 210으로 낮추기.** 길 픽셀이 1/4로 떨어져 짧은 갈래가 사라진다. 비용은 훑는 범위로 푼다.
- **`bandWidthDivisor = 1.5`를 X 배정과 같은 커밋에서 손대기.** 겹침 이중계수 보정을 뭉뚱그린 상수라 건드리면 `minBandWidthRatio` 관문까지 재캘리브레이션이 딸린다.
- **`minComponentPixels` 류를 되살려 관문으로.** 해상도 240~1065에서 면적비·거리비는 ±6% 불변인데 절대 픽셀은 무너진다는 것이 두 곳에 문서화돼 있다.
- **`AnnotationChunk`를 `Syllable`로 개명.** 그림 경우(`map_deep_05` 육각형 얼굴)가 실재하는 한 이름이 거짓말이 된다.
- **음절 수를 필수 인자로.** `detectReveal`이 "두 장의 그림만으로"라는 자기 소개를 잃고, 그림 주석에는 넣을 값이 존재하지 않는다.
- **자동 정렬(위상 상관·특징점 매칭).** 두 장은 같은 파이프라인이 낸 형제 자산이지 촬영본이 아니다. 어긋나면 버그이지 보정할 신호가 아니고, 정렬기를 넣는 순간 '어긋난 채로 그럴듯하게 도는' 경로가 생겨 문제가 영영 안 보인다.
- **`base.png`를 픽셀까지 재인코딩.** 색 청크만 맞춰라. 한 비트라도 바뀌면 124.5·905.7과 2251·2877·3468이 전부 무효다.
- **`composedAlphaThreshold`를 "안 쓰이니까" 삭제.** 캔버스의 24%(35,097px)가 alpha<250인데 지금은 두 장이 그 영역에서 일치해서 안 걸릴 뿐이다. 어긋나는 자산 하나면 화면 전체가 '변한 곳'이 된다.
- **마스크를 화면 해상도로 미리 굽기.** 420px 529 KB가 4~9배가 되고 굽기 시간도 곱해진다. 확대 보간이 임계를 흐리지 않는 것은 이미 보장된다(임계가 코드축에서 선형이라 lerp와 교환된다).
- **`shouldRepaint` 완화 / 페인터에 k 상수 부활 / `base` 생략 / `Picture.toImage` → `toImageSync`.** 각각 재굽기 감지 유일 경로 파괴, 표현 계약 이중화, 진행도 0의 그림 상실, UI 스레드가 래스터 대기.
- **diff 픽셀 루프 최적화.** 0.45 ms — prepare의 1.5%다.
- **isolate 추가 분할·SIMD.** 왕복 비용이 이미 0이고 병목은 산술이 아니라 훑는 픽셀 수다(형태정리 시간이 마스크 크기와 무관하다는 것이 증거). web 대상이라 `Float32x4`는 어차피 못 쓴다.
- **컨트롤러에 curve / 주 획 시간을 픽셀로 되돌리기 / `_primaryMillis`에 곡선.** 각각 가감속 이중 적용, `purity_test:164-175` 위반, `purity_test:178-192` 위반.
- **`kRevealHiddenSegment = 255` 이동, `within`을 Uint8로, k를 길 해상도 때문에 올리기.** 순서대로 254 세그먼트 상한 규약 연쇄, 문구 진행도(폭 14~51px)에 계단, k=128이어도 길 코드는 76→79로 4%만 늘고 선단만 10.6→2로 좁아져 이음매가 전부 드러난다.
