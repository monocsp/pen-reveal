# 굽기 성능 — 구현 전략 비교

## 이 문서가 비교한 것과 비교하지 않은 것

굽기(`bakeOneStrokeOrder`)를 **어떤 기판에서 돌릴 것인가**(순수 Dart · C/FFI · 플랫폼 네이티브 · GPU 셰이더 · python)를 실제로 구현해 재고 비교한 결과다. **알고리즘 자체를 바꾸는 축은 이번에 다루지 않았다** — 형태 정리를 뺄 수 있는지, Zhang-Suen 대신 다른 세선화를 쓸 수 있는지, 뼈대 없이 갈 수 있는지는 재지 않았다(§아직 안 물어본 질문). 그래서 이 문서의 결론은 "같은 계산을 어디서 돌릴 것인가"에 한정된다.

환경: Apple M1 Max / macOS 25.5.0 / Dart 3.11.0. 픽스처는 정본 10종(`example/tool/out/rgba/*_<longSide>.bin`). 굽기 해상도 420 = 347×420 = 145,740 px.

**정본 기준선을 하나로 박는다.**

> **420 · Dart AOT · `bakeOneStrokeOrder`(orig) = 14.78 ms** (`final_aot.txt`, 10종 중앙값, warmup 3 · 25회).
> 210 = 3.68 ms, 840 = 69.29 ms.
> 같은 하네스의 **중립 대조군**(`bakeOpt` 를 모든 플래그 off 로 호출한 `opt-none`)은 210/420/840 에서 **3.89 / 16.09 / 73.47** 이다.
> **전략 간** 배수는 orig(14.78)를 분모로 쓴다. **옵션 간**(①~⑧) 배수는 대조군(16.09)을 분모로 쓰고, orig 기준 배수를 병기한다.
> 다른 세션에서 나온 값을 인용할 때는 **그 세션의 기준선을 함께 적는다.**

**프로토콜은 실험마다 다르다.** "모든 수치는 10종 중앙값"이라고 뭉뚱그릴 수 없다 — 표의 프로토콜 열을 볼 것. 특히 GPU 는 워밍업이 0회다.

실측과 추정을 구분해 표기했다. 표기가 없으면 실측이고, 산술로 유도했거나 재보지 않은 값은 **(추정)**, 아예 안 잰 것은 **(미측정)** 을 붙였다.

## 지금 어디에 시간이 쓰이나

### 파이프라인 전체 (Flutter DEBUG/JIT, 420, 10종 중앙값)

| 단계 | ms | 스레드 |
|---|---:|---|
| **prepare 전체** | **29.22** | — |
| ├ 디코드 ×2 | 5.71 | UI |
| ├ rgbaAt ×2 (엔진 리샘플) | 5.67 | UI / GPU |
| ├ **detectReveal** | **21.72** | isolate (`compute`) |
| │  ├ **bake** | **19.12** ← 핫스팟 | isolate |
| │  ├ X 분할 | 0.72 | isolate |
| │  ├ 글씨 분할 | 0.07 | isolate |
| │  └ (미귀속) | 1.81 | — |
| ├ compile | 0.58 | UI |
| └ RGBA→ui.Image | 0.50 | UI |

> ⚠️ **이 분해는 산술이 안 맞는다.** 부분 합 5.71+5.67+21.72+0.58+0.50 = **34.18** 로 총계 **29.22** 를 17% 넘는다. prepare 는 순차 경로이므로 부분이 전체를 넘을 수 없다 — 총계와 단계값이 **같은 실행에서 나오지 않았다.** detectReveal 안쪽도 19.12+0.72+0.07 = 19.91 로 **1.81 ms(8.3%)가 미귀속**이다. 그래서 **비중(%)은 계산하지 않는다.** 한 번의 prepare 안에서 총계와 모든 단계를 동시에 계측해 다시 재기 전까지, 아래에 나오는 "UI 스레드 약 11.9 ms" 와 §커널 사다리의 "prepare 약 12.6 ms" 는 **자릿수 감각으로만** 읽어야 한다.

UI 스레드에 남는 것은 대략 **11.9 ms**(디코드 5.71 + rgbaAt 5.67 + 0.50)다 — 위 경고를 감안한 어림값이다. 나머지는 isolate 로 나가 있다.

**isolate 왕복 비용은 실측상 유의미하지 않다(sync 21.72 vs compute 21.72).** 다만 두 가지를 정정해 둔다.

- **원인 설명이 절반만 맞았다.** 이전 판은 "TypedData 가 복사가 아니라 이전되기 때문"이라고 단언했다. 정확히는 `compute` 의 **반환 경로**만 `Isolate.exit` 로 결과 그래프를 이전하고(zero-copy), **인자 경로는 복사**다. 그리고 어느 쪽이든 145 KB 는 마이크로초 단위라 21.72 ms 옆에서 안 보인다 — **왕복이 싼 진짜 이유는 메모리 모델이 아니라 데이터가 작아서다.** 이 메커니즘은 **이번에 소스로 확인하지 않았다(미검증).**
- **두 값이 소수 둘째 자리까지 같은 것 자체가 의심스럽다.** 이 문서가 스스로 인정한 6~9% 회차 노이즈와 양립하지 않는다. 왕복이 실제로 시계 안에 있었는지(콜백 본체만 잰 것은 아닌지) **재확인이 필요하다.** 이 값은 주어진 실측을 인용한 것이고 반복 횟수·환경이 기록돼 있지 않다.
- ⚠️ **`compute` 는 호출마다 isolate 를 새로 띄운다.** 위 "왕복 0" 은 **데이터 전달** 비용이지 **개설(spawn)** 비용이 아니다. 릴리스 모바일 콜드 스폰은 밀리초 단위일 수 있고 **아직 안 쟀다(미측정)**. 굽기가 화면당 1회라면 스폰도 화면당 1회이므로 이 비용은 bake 최적화로 줄지 않는다 — 장수 워커 isolate 를 쓰면 사라진다.

순수 코어만 따로: JIT bake 18.82 / AOT bake 16.10 → **AOT 이득 약 15%**.

### bake 내부 분해 (Dart AOT, 420)

두 세션이 독립적으로 쟀고 값이 일치한다.

| 단계 | ms | bake 대비 | 데이터 병렬? |
|---|---:|---:|---|
| 이진화 | 0.10 | 0.7% | ○ |
| **형태 정리 (닫힘×2·열림×2 = 8패스)** | **8.66 ~ 8.92** | **56%** | ○ |
| **Zhang-Suen 세선화 (반복 수렴)** | **4.52 ~ 4.62** | **29%** | ○ (수렴 검사만 순차) |
| 정규화 (0~254 접기) | 1.17 ~ 1.22 | 7.7% | ○ |
| BFS 전파 | 0.44 ~ 0.47 | 2.9% | △ (근사 필요) |
| 그래프 구축 + 잔가시 제거 + DFS 한 붓 | 0.27 ~ 0.59 | 1.7 ~ 4.0% | × (본질적 순차) |

**여기서 통념 하나가 뒤집혔다.** "해시맵 그래프(`Map`/`Set`)와 `used` 집합 해싱이 무겁다"는 가정으로 자료구조 교체를 요청받았지만, 실측하면 **그래프를 다루는 순회 계산 전부가 bake 의 4% 미만**이다. 거기서 아무리 잘해도 0.6 ms 를 못 넘는다. 실제 무게는 **21만 픽셀을 통째로 여러 번 훑는 두 커널(형태 정리 + 세선화 = 85%)** 에 있었다.

본질적 순차부는 전부 합쳐 **6.9%** 다. 그런데 **병렬화 = GPU 가 아니다.** 형태 정리·세선화·정규화(85%)는 가로 밴드로 잘라 헤일로 1 px 만 교환하면 되는 전형적 데이터 병렬이고, Dart 에는 **isolate 풀**이라는 순수 답이 있다 — 웹·`dart test`·의존성 0·사본 0 을 하나도 안 잃는다. **이번에 못 쟀다(미측정).** 아래 GPU 절이 "왕복 비용이 계산을 넘는다"고 결론 내리는 것은 GPU 에 대한 판정이지 병렬화 일반에 대한 판정이 아니다.

### ⚠️ 기준선 변동 세 가지

**(1) 하네스 노이즈.** 같은 소스라도 바이너리 내 코드 배치만 달라지면 6~9% 가 움직인다. 원본을 한 글자도 안 고친 축자 복사본이 15.92 vs 14.99 ms 로 나온 실측이 있다. 그래서 **1.1배 미만의 차이는 유의미하다고 주장하지 않는다.** 세션별 420 기준선은 14.78 / 15.90 / 15.96 / 16.10 / 16.27 로 흩어지지만 모두 ±5% 안이다.
덧붙여 **단일 해상도의 1.1~1.2배 차이는 해상도 추세가 일관될 때만 채택한다.**

**(2) `orig` 와 `bakeOpt` 사이에 +6~9% 의 계통 단차가 있다.** 하네스가 등록해 둔 중립 대조군(`opt-none`, 모든 플래그 off)이 orig 보다 계통적으로 느리다 — 210: 3.68 vs 3.89(+5.7%), 420: 14.78 vs 16.09(+8.9%), 840: 69.29 vs 73.47(+6.0%). 같은 라운드에 끼워 돌린 두 번째 orig 는 14.84 로 0.4% 안이라 orig 쪽은 안정적이다. 즉 **경로가 다른 두 함수를 직접 나눈 배수에는 이 단차가 통째로 섞여 있다.** 문서의 1.1배 규칙에 따라, 옵션 배수는 **대조군 기준을 병기해야만** 인용한다.

**(3) 측정 중 워킹트리가 바뀌었다 — HEAD 가 아니다.** 다른 세션이 `_spread` 를 8-이웃 FIFO BFS → 체임퍼 2-패스로 바꾼 **미커밋 로컬 수정**이 워킹트리에 있다. 확인했다: `git rev-parse --short HEAD` = **c8af051** 이고 `git show HEAD:…/one_stroke_bake.dart` 의 `_spread` 에는 체임퍼가 없다. 즉 이 문서가 "세션 시작 시점(c8af051)"이라 부른 것과 "현재"라 부른 것은 **같은 커밋**이고, 아래 19.38 은 HEAD 가 아니라 **누군가의 미커밋 편집**이다.

그 워킹트리 상태를 재면 bake 가 **420 에서 +4.20 ms, 840 에서 +16.42 ms** 늘고(전파 단계 0.44 → 약 4.64 ms, 10배), 출력도 달라진다.

> **출력 변화량을 정정한다.** 이전 판은 "길 픽셀의 약 2%(29,444/1,457,400)"라고 적었는데 **분모가 틀렸다** — 1,457,400 은 캔버스 전체 × 10종이다. 실측(반증 세션: `detector.dart` 임계 재현 — |ΔRGB| > 18, composed α > 200, R−G > 35 제외, 420 코퍼스 10종)으로 길 픽셀은 픽스처당 2,254~10,023, **합계 68,285**(캔버스의 1.55~6.88%, 중앙값 약 5.5%)다. 순서값은 길 안에서만 정의되므로 옳은 분모는 이쪽이고, **29,444 / 68,285 = 약 43%** 다. 2% 면 반올림 흔들림으로 읽히지만 43% 면 **연출이 달라진 것**이다.

## 저울을 먼저 정한다 — 무엇이 "같은 결과"인가

이 문서는 지금까지 정확성을 **바이트 동일** 하나로만 쟀다. 그 기준에서는 해상도 낮추기 · 형태 정리 생략 · Guo-Hall · JFA · GPU 고정 패스가 **재보기도 전에** 전부 탈락한다. 실제로 이전 판은 그렇게 탈락시켰고, 그래서 남은 길이 비트트릭뿐이었다.

그런데 산출물은 회계값이 아니라 **연출**이다. 사용자가 보는 것은 500~2000 ms 동안 펜이 지나가는 순서이고, 순서값이 몇 단계 흔들려도 눈에 같으면 같은 제품이다. 그래서 두 번째 저울이 필요하다.

**연출 동등성 (①~⑤ 전부 통과):**
1. 커버리지 — 진행도 1 에서 최종본과 100% 일치
2. `length` / `relativeLength` 가 코퍼스 범위(최단 124.5 · 최장 905.7 · 압축 0.35)와 ±5% 안
3. 뼈대 위상(연결 성분 수 · 분기점 수)이 같음
4. `CrossCalibration` 관문 통과
5. 코퍼스 10종 눈 대조

**①~⑤ 를 통과하면 바이트가 달라도 같은 제품으로 본다.** 아래 표의 "정확성" 열은 **바이트 동일 / 연출 동등 / 미검증** 세 값이다. 지금 "연출 동등"으로 판정된 항목은 없다 — 그 저울로 잰 것이 아직 하나도 없기 때문이다.

⚠️ **GPU 행은 워밍업이 0회다** — 첫 회에 FragmentProgram 파이프라인 컴파일과 텍스처 최초 할당이 들어가고 5회 전부가 중앙값에 들어간다. **GPU 수치는 상한으로 읽어야 한다.** 워밍업 3회를 넣어 재측정하기 전까지 GPU 의 패배 폭은 과대평가돼 있을 수 있다(방향은 §5 의 구간별 비교로 보건대 바뀌지 않을 것으로 보이지만, 그것도 추정이다).

**세 줄 요약**

1. 실측된 최선은 **순수 Dart 비트팩 2.21 ms(6.69배)** 이고, 그보다 싸고 위험이 낮은 **ROI 크롭(1.94배, 커널 무수정, 30줄)** 이 그 앞에 있다.
2. **"네이티브도 GPU 도 순수 Dart 보다 느리다"는 말은 할 수 없다** — 비교된 것은 *최적화 전 C* 와 *최적화 후 Dart* 다. 동일 알고리즘의 네이티브 이식(전체 bake)은 만들지도 재지도 않았고, 부분 실측(§3)은 오히려 **같은 알고리즘이면 C 가 여전히 이긴다**고 말한다. FFI 를 접는 근거는 성능이 아니다.
3. **이 표는 전부 bake 기준이다.** 사용자가 기다리는 값은 `prepare` 29.22 이고 그중 약 11.9 는 굽기 밖(디코드·리샘플)에 있다 — **6.69배를 다 받아도 체감은 약 2.3배다.**

### 2. 순수 Dart · 비트팩 — 6.69배(대조군 7.28배), 실측된 최선

요청 밖에서 붙인 셋이다. **알고리즘은 한 글자도 안 바꾸고 루프가 도는 총량만 줄였다.**

| 항목 | 대상 단계 | 원본 → 변경 후 (ms) | 배수 |
|---|---|---:|---:|
| ⑥ 형태연산 비트팩 (64 px/워드, 시프트+OR/AND) | morph | 8.66 → **0.20** | 44배 |
| ⑦ 세선화 활성목록 (살아있는 전경만 재방문) | thin | 4.52 → **0.60** | 7.5배 |
| ⑧ 마무리 양자화 루프 | finish | 1.17 → **0.24** | 4.9배 |
| **⑥+⑦+⑧** | bake 전체 | 14.78 → **2.21** | **6.69배 / 대조군 16.09 대비 7.28배** |

독립 세션이 비트슬라이스 세선화(이웃 8평면 + 전가산기로 B·A 계산)를 따로 구현해 같은 방향의 결론을 냈다 — 형태 20.1배, 세선화 19.7배, bake 전체 15.96 → 3.21 ms(4.97배). 두 세션의 절대값이 다른 것(2.21 vs 3.21)은 ⑧ 적용 여부와 하네스 차이다.

> 이전 판의 "①~⑧ 전부 → 2.19 (6.75배)" 행은 **삭제했다.** `final_aot.txt` 에 그 값이 없다(그 자리에 해당하는 행은 `all seven + pool 3.03`). 출처 불명 수치였다.

**⑧ 은 하나가 아니라 셋을 함께 바꾼다.** `dart/lib/opt.dart` 의 `finishFast` 분기(154–172행) 기준:

1. maxT 루프를 `for (final v in field)` 이터레이터에서 인덱스 루프로 — 여기서 큰 몫이 나온다,
2. 두 번째 루프에서 픽셀마다 재계산하던 삼항 `(maxT <= 0 ? 1 : maxT)` 를 `den` 으로 루프 밖에 호이스팅,
3. `.clamp(0, 254)` 제거.

⑵⑶ 은 145,740 픽셀을 도는 두 번째 루프에 걸리므로 1.17 → 0.24 의 상당 부분이 거기서 나온다. 부동소수 연산 순서는 그대로여서 바이트가 같다. **⑶ 은 `field[i] ≤ maxT = den` 이라는 불변식에 기댄 실제 의미 변경**이므로(성립하기는 한다) 코드에 `// field[i] <= maxT 이므로 clamp 불필요` 주석을 함께 넣어야 한다. 그래서 위험 등급을 **"없음" → "낮음(불변식 주석 필수)"** 으로 올린다.

정확성: 코퍼스 30조합 + **퍼즈 2,970 비교 불일치 0**. 퍼즈는 비트팩 꼬리마스크 경계(폭 63/64/65, 127/128/129, 191/192/193), 1×1·빈 마스크·꽉 찬 마스크, 워드 경계에 붙은 세로 막대, 알파 임계값 언저리(126~130)를 노렸다.

위험: **⑧ 낮음(주석 필수) · ⑦ 낮음 · ⑥ 만 비싸다** — 행 꼬리비트 마스킹·워드 경계 캐리·`>>>` 셋 중 하나만 틀려도 조용히 틀린 답을 낸다. 넣으려면 퍼즈 테스트를 같이 넣어야 한다. 부담스러우면 ⑤(분리 슬라이딩, 2.84 ms)가 훨씬 읽히는 절충안으로, ⑥ 이득의 3분의 2를 평범한 코드로 가져간다.

### 3. C + `dart:ffi` — 3.3~3.7배. 그리고 이 비교는 언어가 아니라 알고리즘 차이였다

Dart 정본 전 단계를 C 로 1:1 이식했다(452줄). `Map`/`Set` 삽입 순서, `used` 해싱, `Float32List` 저장, `double.round()` 반올림까지 복제했다.

| 측정 | 420 (ms) | 정본 14.78 대비 |
|---|---:|---:|
| C `-O2` (계산만) | 4.234 | 3.49배 |
| C `-O3 -march=native` | 4.003 | 3.69배 |
| **`dart:ffi` end-to-end** | **4.425** | **3.34배** |
| 재측정 (다른 세션, 동일 조건) | 4.26 | 회차 변동 −4% |

> **"end-to-end" 의 범위를 정정한다.** 입출력 `malloc`·복사·호출은 시계 안이지만, **12 MB 스크래치 할당은 시계 밖이다 — 프로세스당 1회 잡고 재사용한다.** `c/main.c` 는 `bake_scratch_new` 를 파일마다 루프 **밖에서** 부르고 12회 호출이 그 버퍼를 공유한다(`bake.h` 기준 nb·stack·tval 합쳐 420 에서 12 MB 초과). 반면 Dart 정본은 호출마다 morph 8패스분 `Uint8List` 를 새로 잡는다. 이전 판의 "malloc·복사 전부 시계 안"은 사실과 달랐다.

마샬링 비용은 무시할 수준이다: 420 에서 +0.19 ms, 840 에서 +0.06 ms. leaf 호출 오버헤드는 **6.8 ns**. 바이너리도 문제가 아니다 — 스트립한 dylib 33,808 B, Android 4 ABI 합쳐 ~140 KB.

정확성: 30 픽스처 × 3 빌드 = **2,292만 픽셀 전부 바이트 동일**. `maxT` 도 소수 4자리까지 일치. `-O3 -march=native` 도 결과를 안 바꿨다 — 단, **`-ffast-math` 를 켜면 이 보장이 깨진다.** `-march=native` 는 출하할 수 없으므로 실기기 기대치는 `-O2` 기준으로 잡아야 한다(둘의 차이는 3~6%).

#### ⚠️ 결론 정정 — "네이티브가 순수 Dart 보다 느리다"는 말은 성립하지 않는다

이전 판은 "순수 Dart 비트팩(2.21)이 FFI(4.26)보다 1.9배 빠르다 → 순수성을 팔고 손해까지 보는 거래"라고 썼다. **이건 교란된 비교다.** C 이식본은 헤더 주석대로 **스칼라 정본의 1:1 이식**이고 비트팩이 없다(전 파일에서 시프트 연산이 `used` 비트마스크 2곳뿐). 반면 2.21 은 ⑥⑦⑧ 을 넣은 **다른 알고리즘**이다. 언어 축과 알고리즘 축을 동시에 바꿔 놓고 언어 축의 결론을 냈다.

**알고리즘을 고정해 반증했다.** `opt.dart` 의 `_morphBits` 를 C 로 축자 이식하고(`xcheck/cbits.c`) 정본 픽스처 10종·420 에서 재니 중앙값 **0.1085~0.1475 ms**(두 차례 실행, 파일별 25회 중앙값 → 10종 중앙값, M1 Max)로, 같은 일을 하는 **Dart 비트팩 morph 0.198 ms 보다 1.3~1.8배 빠르다.** 일을 덜 한 것도 아니다 — `xcheck/verify.c` 로 스칼라 C morph(닫힘×2·열림×2)와 대조해 10종 전부 diff = 0 이다.

그러므로 실측이 말할 수 있는 것은 둘뿐이다.

- **(i)** 같은 알고리즘에서 C 는 Dart AOT 보다 빠르다 — 스칼라 전체 bake 3.3~3.7배, 비트팩 morph 구간 1.3~1.8배. **방향이 일관된다.**
- **(ii)** 알고리즘을 고치는 것만으로 6.69배가 나오므로, **비트팩을 먼저 넣으면 FFI 가 노릴 남은 여지는 morph + thin 합쳐 0.8 ms** 다.

**따라서 FFI 를 접는 근거는 성능이 아니다.** 절대 이득이 0.8 ms 라 네이티브 경계 비용(웹 부재 · 쌍둥이 사본 · CI · `purity_test` 의 정신)을 정당화하지 못한다는 것이 정확한 논거이고, 그 논거는 성능과 무관하게 성립한다.

#### 그리고 모든 절대값은 웜 스틸스테이트다

실측(`xcheck/cold.c`, `c/bake.c` 를 그대로 링크, 420·10종): 스크래치를 새로 잡은 직후의 **첫 굽기 4.875 vs 웜 중앙값 4.496 ms(+8.4%)**, **프로세스의 맨 첫 굽기는 12.414 vs 5.039 ms 로 2.46배**다. 굽기는 정의상 그림당 한 번, 그것도 앱에서 처음 도는 코드라 **실제로 겪는 것은 후자 쪽이다.** 이 문서의 모든 절대값은 하한이다.

### 4. 플랫폼 채널 (Swift/Kotlin) — 직렬화는 문제가 아니었고, 사본 수가 문제다

macOS Runner 에 Swift echo 핸들러를 직접 붙여 왕복을 실측했다. 수치는 산출물(`gpu_result.txt`) 값으로 통일하고 자릿수를 회차 변동 폭에 맞춰 줄였다.

| 측정 | ms (50회 중앙값) |
|---|---:|
| `MethodChannel` 빈 호출 왕복 | ≈0.02 |
| `Uint8List` 145,740 B 왕복 (420) | ≈0.06 |
| `Uint8List` 582,120 B 왕복 (840) | ≈0.22~0.24 (회차 간 9% 변동) |

"직렬화가 비쌀 것"이라는 가설은 기각됐다 — typed-data 는 바이트 복사 한 번이고 계산 옆에서 2% 다. 전체 예상은 **약 3.5 ms (추정** — C 계산 3.42 + 왕복 0.06 의 산술, Swift/Kotlin 구현은 실제로 안 만들었다**)**.

채널의 결격은 성능이 아니라 구조다. Swift·Kotlin **두 벌의 알고리즘 사본**(Dart 정본까지 세 벌)을 픽셀 단위로 계속 일치시켜야 하고, 웹·데스크톱 경로가 없고, 비동기라 `compute` isolate 에서 쓰려면 `RootIsolateToken` + `BackgroundIsolateBinaryMessenger` 배선이 필요하다. **네이티브로 가야 한다면 모든 축에서 FFI 가 낫다.**

### 5. GPU FragmentProgram — 실제로 짜서 돌렸고, 왕복 비용이 계산을 넘는다

`flutter build macos --release`(Impeller/Metal)에서 실행했다. 소프트웨어 래스터가 아니다.
⚠️ **프로토콜: 워밍업 0회 · 5회 전부를 중앙값에 포함**(수렴검사 항목은 3회). 첫 회에 파이프라인 컴파일과 텍스처 최초 할당이 들어가므로 **아래 값은 상한이다.** 워밍업 3회로 재측정하기 전까지 GPU 의 절대 열세 폭은 확정된 것이 아니다.

| 측정 | 420 (ms) | 840 (ms) | 비고 |
|---|---:|---:|---|
| `decodeImageFromPixels` 업로드 1회 | 0.27 | 0.63 | |
| **`toByteData` 읽기 1회** | **0.75** | 1.51 | 계산 0. 이것 하나가 비트팩 CPU 의 형태+세선화 전체(0.80)에 육박한다 |
| 이진화1 + 형태8 + 세선화20 = **29패스 + 읽기 1회** | **2.96** | **5.30** | |
| 패스당 한계비용 (29패스 기준) | ≈0.08 | ≈0.13 | 패스 자체는 싸다 |
| 패스마다 CPU 로 읽어 **수렴 검사**할 때 (패스당) | 0.84 | 1.70 | 20패스면 16.8 ms — 현행 세선화(4.62)보다 3.6배 느리다 |

**같은 구간끼리 대야 한다.** 위 2.96 / 5.30 은 bake 전체가 아니라 **이진화+형태+세선화 구간만**이다. 같은 구간의 비트팩 CPU 는 420 에서 morph 0.20 + thin 0.60 = **0.80 ms**, 840 에서 약 **3.2 ms**(픽셀 4배 산술, 추정)다.

| 구간 비교 | 420 | 840 |
|---|---:|---:|
| GPU (형태+세선화 구간) | 2.96 | 5.30 |
| 비트팩 CPU (같은 구간) | 0.80 | ≈3.2 (추정) |
| **GPU 의 열세** | **3.7배** | **1.7배** |

**왕복 비용이 픽셀에 상각되어 격차가 줄기는 하지만 840 에서도 역전하지 않는다.** bake 전체로 환산하면(실측 구간 + 순차부 산술) 420 ≈ **5.3 ms**, 840 ≈ **14.5 ms** **(추정)** 으로, 비트팩 전체(2.21 / 8.57)에 각각 2.4배 · 1.7배 진다.

**수렴을 포기해야 한다.** 실측 반복 수는 420 에서 중앙 14·최대 20, 840 에서 중앙 26·최대 36. 패스마다 읽으면 위 표대로 이득이 소멸하므로 "32패스 고정" 말고는 길이 없는데, 그 상한이 못 보던 입력에서 깨지면 **덜 세선화된 뼈대 → 다른 그래프 위상 → 다른 한 붓 순서**로 조용히 틀어진다. 상한을 증명할 방법이 없다.

**정확성은 부분 검증이고, 검증 범위가 정작 걱정하는 조건을 안 밟았다.** 합성 마스크 128×96(**12,288 px, 정본 420 의 8%**)에서 dilate 1패스와 세선화 20패스가 헤드리스 소프트웨어 Skia 와 Metal 양쪽에서 **0 px 차이**를 냈고, R 채널에 0/255 말고 중간값이 없었다. 다만 산출물이 스스로 적어 두었듯 **이 케이스는 CPU 수렴이 3라운드**다 — GPU 20패스 중 17패스가 이미 수렴한 그림에 대한 무동작이었다. 즉 **"고정 상한이 수렴 횟수를 크게 웃도는 조건"만 시험한 셈**이고, 문서가 위험하다고 지목한 조건(420 최대 20, 840 최대 36 — 상한에 육박하거나 넘는 경우)은 검증되지 않았다. 정본 코퍼스 420 전체, Vulkan/Android, WebGL, GLES2 `mediump`(fp16) 도 안 재봤다. `texture(uTex, p/uSize)` 로 텍셀 중심을 되찾는 구조라 fp16 이면 `uSize ≳ 1024` 에서 어긋난다.

따라서 **"GPU = 비결정적은 이 파이프라인에서 틀렸다"는 일반 명제는 세우지 않는다.** 정확한 진술은 이것이다 — **이 한 케이스(12,288 px, 수렴 3라운드)에서는 백엔드 간 일치했다. 일반화하려면 정본 코퍼스 420 전체를 상한 근처 회전수로 재봐야 한다.**

**부수 결론: 지금 재현성을 깨고 있는 것은 `rgbaAt` 의 `FilterQuality.medium` 엔진 리샘플이다**(길 시간 697 vs 641 ms, relativeLength 0.131 vs 0.094). 연속값을 내는 필터 커널이라 이진 마스크 연산과는 종류가 다르다. 다만 **이것을 걷어내는 것은 공짜가 아니다.**

- **(i)** 지금 GPU 가 처리하는 rgbaAt ×2 = 5.67 ms 가 CPU 로 넘어온다. **순수 Dart 리샘플러 비용은 안 쟀다(미측정).** 이건 비트팩이 아끼려는 폭과 같은 자릿수다.
- **(ii)** 리샘플 결과가 바뀌면 마스크가 바뀌므로, 420 기준으로 굳은 코퍼스 상수(124.5 / 905.7 / 0.35)와 `CrossCalibration` 관문이 **840 을 올릴 때와 똑같이 무효화된다.**

**그러므로 이건 성능 항목이 아니라 캘리브레이션 항목이고, 840 판정과 같은 대기열에 넣어야 한다.** 해상도 변경은 캘리브레이션 때문에 막으면서 리샘플러 변경은 부수 결론으로 권하는 것은 일관되지 않는다.

### 6. python 세 방식 — 전부 현행보다 느리다

정본을 순수 python 과 numpy 두 벌로 옮겨 같은 픽스처에 쟀다. 배수는 정본 기준선(3.68 / 14.78 / 69.29) 기준이고, 괄호 안은 **같은 세션의 Dart AOT 기준선**(4.08 / 16.27 / 75.04) 기준이다.

| 구현 | 210 | 420 | 840 |
|---|---:|---:|---:|
| Dart AOT 정본 기준선 | 3.68 | 14.78 | 69.29 |
| (같은 세션 기준선) | 4.08 | 16.27 | 75.04 |
| numpy 벡터화 | 5.18 — 1.41배 느림 (1.3배) | 22.48 — **1.52배** (1.4배) | 134.44 — **1.94배** (1.8배) |
| 순수 python | 18.01 — 4.89배 (4.4배) | 72.20 — **4.89배** (4.4배) | 311.34 — 4.49배 (4.1배) |

**numpy 를 최대한 밀어붙여도 정본보다 빠른 지점이 하나도 없고, 해상도가 올라갈수록 격차가 벌어진다.** 이유가 구조적이다. 벡터화된 세선화가 numpy 시간의 63%(14.0/22.1 ms)를 먹는데, 수렴할 때까지 격자 전체를 7~12번 훑으며 매 반복 15만 칸 전부에 30여 개 임시 배열을 만든다. Dart 는 켜진 픽셀만 훑는다. **길이 캔버스의 1.6~6.9%(중앙값 약 5.5%) 뿐이라** 성길수록 numpy 가 손해다. 나머지(그래프·잔가시·DFS)는 **본질적 순차라 벡터화가 안 되고** numpy 를 써도 순수 python 속도 그대로다.

연결 방식별로도 전부 진다.

| 방식 | 실측 | 결격 |
|---|---|---|
| **(a) 서버 + HTTP** | localhost(RTT≈0) 왕복 **24.5 ms**(전송 약 2 ms) | 네트워크가 공짜여도 이미 14.78 보다 1.66배 느리다. 실기기 55~105 ms **(추정: 하한 24.5 + 모바일 RTT 30~80)**. 오프라인이 죽는다 |
| **(b) 기기 내장 CPython** | 기동 17.6 ms, numpy import 까지 **58.9 ms**. numpy 설치본 33.5 MB, stdlib 78.2 MB | Chaquopy·python-for-android 는 Android 전용. iOS 는 CPython 3.13 tier-3 이고 Flutter 임베드 플러그인도 numpy iOS 휠도 실용 단계가 아니다 **(추정)**. 앱 **+15~40 MB (추정)**. 그 대가로 1.52배 느려진다 |
| **(c) python 빌드타임 산출물** | 런타임 비용 0 | **이 레포가 의도적으로 지운 길이다 — python 사본이 정본과 갈라졌다.** 기각 사유는 *사전계산이라서*가 아니라 *python 사본이라서*다 (↓ 다음 절) |

**곁가지 성과가 하나 있다.** python 은 **오프라인 참조 구현으로서는 훌륭했다.** 30/30 이 바이트 단위로 일치했고, 그 과정에서 정본의 암묵 규약 셋이 드러났다 — ① `area` 는 원본 마스크가 아니라 **형태정리본**의 픽셀 수다(원본을 쓰면 `minLen` 이 15 대 11 로 갈려 잔가시 제거가 달라진다), ② 시간장이 `Float32List` 라 대입 시점에 float32 로 깎인다, ③ BFS 동점 픽셀의 소유권은 **큐 삽입 순서**로 갈린다. 셋 다 문서에 없고 셋 다 결과를 눈에 안 띄게 바꾼다. 이건 검증 도구의 가치이지 런타임을 옮길 근거가 아니다.

### 6.5 사전 굽기 (정본 Dart, 빌드/발행 시점) — 런타임 0

이전 판은 이 칸을 python 쌍둥이 이야기로 덮어 지웠다. **이 레포가 지운 것은 "사전계산"이 아니라 "python 사본"이다.**

`dart run tool/bake_orders.dart` 가 `bakeOneStrokeOrder` 를 **그대로 불러** 순서맵을 자산으로 구우면 **사본은 0벌**이고 `one_stroke_bake.dart:6-10` 의 "쌍둥이를 다시 만들지 말 것"에 걸리지 않는다. 그리고 이 앱이 실제로 그리는 그림은 `example/assets/maps/<key>_{base,composed}.png` **10종, 즉 빌드 시점에 전부 알려진 고정 자산**이다(`corpus_maps.dart`/`availableCorpusKeys`).

- 순서맵은 w×h 바이트 한 장 — 420 에서 145 KB, PNG 로 접으면 훨씬 작다.
- **자산이면 굽지 않고 읽는다(0 ms). 런타임에 들어온 그림이면 코어로 굽는다.** 사전계산은 런타임 굽기를 *대체*하는 게 아니라 *앞에 까는* 것이므로 코어의 존재 이유는 그대로 남는다 — 이전 판이 남긴 유일한 반론("런타임 입력을 못 다룬다")은 성립하지 않는다.
- 그림이 서버에서 오는 제품이라면 같은 원리를 발행 파이프라인에 둔다 — **요청당 RPC(24.5 ms)가 아니라 발행당 1회**, 순서맵을 그림과 함께 내려준다. 이 표준적인 답을 이전 판은 아예 검토하지 않았다.
- 순수성 위반 0, 웹 포함 전 플랫폼 동작.

**규율 하나가 따라온다:** 자산에 **알고리즘 버전**을 박고, CI 가 "구운 자산 == 지금 코어가 내는 바이트"를 대조해야 한다. 그 대조가 곧 쌍둥이 갈라짐의 반대말이다.

### 7. web — 두 개의 다른 저울을 분리한다

이전 판은 bake 전체와 형태+세선화 구간을 한 열에 올렸다. 쪼갠다.

**표 A — bake 전체** (`bench_web.dart`/`webfull.dart` 가 `bakeOneStrokeOrder` 를 실제로 호출)

| 컴파일 타깃 | 420 bake 전체 (ms) | 같은 소스 네이티브 AOT | 배수 | 프로토콜 |
|---|---:|---:|---:|---|
| dart2js (node/V8), 스칼라 | 28.0 | 17.7 | 1.58배 느림 | 3 · 9 · **단일 마스크 1종** |
| dart2wasm (node/V8), 스칼라 | 33.8 | 17.7 | 1.91배 느림 | 3 · 9 · 1종 |
| dart2wasm, 다른 지도, 스칼라 | 19.663 | 11.97 | 1.64배 느림 | 3 · 9 · 1종 (다른 입력) |
| **dart2wasm, 스칼라 (재측정)** | 27.2~27.6 | 14.78 | 1.8~1.9배 느림 | warmup 3 · 9회 중앙값 · 1종 (node v22.15.1) |
| **dart2wasm, 비트팩 ⑥⑦⑧** | **3.61~3.79** | 2.21 | **1.6~1.7배 느림** | 동상 (비트팩 vs 정본 불일치 0 px) |

**표 B — 형태+세선화 구간만** (같은 마스크, `web/bench.dart:340-359`)

| 타깃 | 구간 (ms) | 네이티브 | 배수 |
|---|---:|---:|---:|
| dart2wasm, 비트팩 | 0.664 | 0.635 | 1.05배 |

> **표 B 를 표 A 에 대입해 bake 전체를 추정하지 마라** — 입력·구간·기준선이 다르다. 이전 판이 "비트팩 0.664 → 사실상 네이티브 속도"라고 쓴 것은 **구간 값을 bake 전체 열에 올린 단위 혼동**이었다. 산술로도 드러난다: 네이티브 스칼라 bake 17.7 이 0.635 가 되려면 27.9배여야 하는데 코퍼스 실측 배수는 6.69배다.
> web 행은 전부 **정본 10종 중앙값이 아니라 단일 하드코딩 마스크**다.

**정정된 서사:** 비트팩은 웹에서도 그대로 먹어 **27.5 → 3.6 ms 로 약 7.3배** 줄지만, **네이티브 대비 1.6~1.7배라는 wasm 페널티는 스칼라(1.58~1.91배)와 똑같이 남는다.** i64 가 그대로 기계 명령이 되는 것은 맞지만 **그것이 페널티를 없애 주지는 않는다.** 게다가 wasm 이 가장 불리한 구간(Map/Set·포인터 추적 = order·spread·finish)은 표 B 에서 통째로 빠져 있었다.

웹에는 FFI 도 플랫폼 채널도 **없다**. 그리고 Flutter 의 `compute` 는 웹에서 진짜 isolate 가 아니라 **콜백을 메인 스레드에서 그냥 실행한다**(소스 확인: `_isolates_web.dart` 가 `await null;` 뒤 `return callback(message);` 이 전부).

**즉 웹에서 아픈 건 "28 ms 가 느려서"가 아니라 "28 ms 동안 UI 가 멈춰서"다.** 답은 둘인데 — **코어를 빠르게 만들기**와 **web worker 오프로딩** — **전자는 쟀고 후자는 안 쟀다(미측정).** dart2wasm 의 worker / `--shared-memory` 경로가 이 파이프라인에서 실용적인지는 모른다. 둘은 배타적이지도 않다. 다만 비트팩 후 웹 bake 전체가 **3.6 ms** 로 16.7 ms 예산 안에 들어오므로, **"웹의 답으로 네이티브 코드가 필요하지는 않다"** 는 결론은 유지된다.

⚠️ **함정(실측): `Uint64List` 는 dart2js 에서 `UnsupportedError: Uint64List not supported on the web` 로 죽고 64비트 정수 리터럴은 컴파일 에러다.** dart2wasm 은 정상이다. dart2js 도 지원해야 하면 `Uint32List` 판(32 px/워드)을 하나 더 두면 되고, 이득은 대략 절반 **(추정 — 안 재봤다)**.

| **⚠️ 미커밋 워킹트리 (체임퍼 `_spread`)** | — | 19.38 | 86.11 | — |

읽을 것 셋.

**현행은 초선형이다** (픽셀 4배당 4.7배). 세선화 반복 횟수가 해상도와 함께 늘기 때문이다 — 하위 패스 실측이 420 에서 중앙 14·최대 20, 840 에서 중앙 26·최대 36 이다.

**비트팩만 선형 아래로 내려간다** (3.3~3.9배). 픽셀당 상수를 1/64 로 접었으므로 해상도가 커질수록 상대 이득이 커진다: 210 에서 5.5배 → 420 에서 6.7배 → **840 에서 8.1배**.

**GPU 는 스케일링이 좋지만 역전하지 못한다.** 왕복 비용이 고정이라 픽셀이 늘수록 상각된다. 다만 **같은 구간으로 맞춰 대면 420 에서 3.7배, 840 에서 1.7배 진다.** 이전 판이 "840 에서 5.37 이 비트팩 전체 8.57 과 붙는다"고 쓴 것은 **부분 구간과 전체를 같은 저울에 올린 것**이었다 — 인용한 두 수는 오히려 GPU 쪽이 작았다. bake 전체로 환산하면 840 에서도 ≈14.5 vs 8.57 로 진다.

## 그래서 뭘 해야 하나

### 0순위 — 굽기를 줄이지 말고 **안 하게 만든다** (제품 결정)

**진입 1회 경로에 한해서는, 프레임 예산 비교가 범주 오류다.** 굽기는 프레임 안에서 도는 일이 아니라 화면 진입 시 1회 도는 일이다. 설계 의도가 소스에 명시적으로 박혀 있다 — `reveal_preparer.dart:17-18`, `one_stroke_bake.dart:11-15`, `reveal_bench.dart:7-12`. 프레임마다 도는 것은 굽기가 아니라 `paint()` 다.

**그러나 리듬 슬라이더 드래그 경로에서는 범주 오류가 아니다.** `reveal_bench.dart:94-97` 의 `didUpdateWidget` 이 `old.timing != widget.timing` 이면 `_bake()` 를 부르고, `main.dart:239` 의 key 에는 timing 이 없다(주석이 "timing 은 key 에 넣지 않는다… `didUpdateWidget` 이 알아서 다시 굽는다"라고 명시). **슬라이더 드래그 한 스텝마다 prepare 전체가 돌고, 그중 UI 스레드에 남는 약 11.9 ms(DEBUG/JIT)가 드래그 제스처 프레임 안에 들어간다.** 이 경로는 실제로 프레임을 떨어뜨리는 것이 맞고, **드래그 중 프레임 타임은 안 쟀다(미측정).**
(같은 근거를 두고 0순위는 "설계 주석"으로 인용하고 2순위는 "주석의 전제이지 코드의 보장이 아니다"라며 뒤집는다 — 그 모순을 여기서 정리했다. **주석은 진입 경로에서만 지켜지고 있다.**)

⚠️ **29.22 ms 는 Apple M1 Max · Flutter DEBUG/JIT 값이다.** 이 문서가 840 판정에 쓴 것과 **같은 저사양 배율 3~6배를 420 에도 적용하면** prepare **88~175 ms (추정)**, 그중 UI 스레드 몫이 **36~71 ms (추정)** 다. 후자는 전환 애니메이션 뒤에 "숨는" 크기가 아니라 그 위에 **프레임 드랍으로 얹히는** 크기다. 즉 0순위의 정확한 상태는 "릴리스 실기기에서도 괜찮다"가 아니라 **"릴리스 실기기를 아직 안 재서 모른다, 그리고 재는 것이 다른 무엇보다 먼저다"** 이다.

> **`kMapBakeLimit` 을 근거로 쓰지 않는다.** 참고로 원본 앱은 굽기에 3초 **실패 타임아웃**을 걸어 둘 만큼 느린 일로 취급했다. 하지만 이건 UX 예산이 아니라 **실패 판정선**이므로 "1% 니까 충분하다"의 근거가 되지 못한다 — HTTP 30초 타임아웃 대비 1% 인 300 ms 응답을 빠르다고 말할 수 없는 것과 같다. **이 레포의 UX 예산(진입→연출 시작 허용 지연)은 아직 아무도 정하지 않았고, 정하는 것이 §커널 사다리 발동 조건 (i) 의 선행 작업이다.**

**공학이 아니라 제품에서 끝나는 항목이 넷이다. 넷 다 코드가 거의 안 늘고, 넷 다 비트팩 6.69배보다 확실하다.**

- **(가) 모션 감소.** `MediaQuery.of(context).disableAnimations` 가 켜진 사용자에게 순차 연출을 재생하는 것은 접근성 위반에 가깝다 — 크로스페이드로 대체하면 그 사용자에게 굽기는 **0** 이다. 접근성 요구를 지키면 성능 문제가 같이 사라지는 흔치 않은 경우다.
- **(나) 재생 시점에 굽는다.** 지금은 화면 진입 시 무조건 굽는다. 연출을 안 보고 지나가는 경로가 있다면 그만큼이 순이익이다(가시성/제스처 트리거).
- **(다) 기기 티어별 해상도.** 저사양(추정 6배)에서는 420 을 고집하는 대신 210~300 으로 내려앉는 정책이 답일 수 있다 — 사양이 낮을수록 화면도 작아 손실이 덜 보인다(§해상도 손잡이와 맞물린다).
- **(라) 인트로 비트를 규격으로.** "전환 애니메이션 뒤에 숨는다"를 우연에 맡기지 말고 **"펜이 움직이기 전 정적 비트 최소 200 ms"** 를 연출 규격에 적으면 굽기 예산이 **설계상 보장**된다.

### 0.5순위 — 굽기를 **줄이는** 대신 **옮긴다**

- **(a) 착수 시점을 앞으로.** 지금은 화면이 세워진 뒤 `initState` 에서 굽는다(`reveal_bench.dart:86` `unawaited(_bake())`) — 전환 애니메이션과 겹치는 게 아니라 **그 뒤에 붙는다.** 화면을 밀기 **전에** `prepare()` 를 착수해 Future 를 넘기면 200~300 ms 전환이 29 ms 를 통째로 덮는다. 코드 몇 줄이고 릴리스 실기기에서 바로 검증 가능하다.
- **(b) 프리페치.** 코퍼스 칩은 키가 전부 미리 알려져 있다 — 유휴 프레임에 이웃 1~2개를 미리 구워 캐시에 넣으면 칩 왕복이 0 이 된다.
- **(c) 점진 재생.** 연출은 500~2000 ms 인데 t=0 에 필요한 것은 순서장의 앞부분뿐이다. 계획을 (길 → X → 문구) 세그먼트 단위로 흘려보내면 굽기가 끝나기 전에 길을 그리기 시작할 수 있다. **설계 변경이라 값이 비싸다 — 다만 비교에 존재는 해야 한다.**

### 1순위 — 프레임 경로를 잰다 (측정 비용이 가장 싸고, 유일하게 16.7 ms 예산과 직접 겨룬다)

`SequentialRevealPainter.paint()` 는 매 프레임 `drawImageRect ×3` + **`saveLayer ×2`** + `ColorFilter.matrix` 를 화면 전체 사각형에 돈다(`sequential_reveal.dart:87-103`, **소스 확인**). 중첩 `saveLayer` 는 오프스크린 타깃을 두 장 잡으므로 태블릿 전체화면·저사양 GPU 에서 프레임 예산을 위협할 **가능성이 있다 (추정 — 이 경로의 페인트 시간은 한 번도 재지 않았다).**

같은 이유로 **릴리스 실기기 `prepare()`** 도 여기서 함께 잰다. `--profile` + timeline 한 번이면 둘 다 나온다. 굽기를 열 가지 방법으로 재는 동안 이 경로는 한 번도 안 쟀다.

### 2순위 — 리듬만 바뀔 때 prepare 를 다시 돌리지 않는다

**가장 싼 수정은 캐시가 아니다.** `RevealPlan` 은 정의상 시간을 모르므로(`purity_test` 가 그걸 잠근다) timing 이 바뀌어도 불변이다. 그러면 필요한 것은 `reveal_bench.dart:94-97` 이 timing 변경에 `_bake()` 전체가 아니라 **`schedule`+`compile`(≈1.1 ms)만** 다시 돌게 쪼개는 것이다 — 새 자료구조도 축출 정책도 없다.

| 경로 | 재굽는 비용 | 실제로 다시 계산할 필요가 있는 것 |
|---|---|---|
| 리듬 슬라이더 (divisions 28/58, 드래그 중 매 스텝) | prepare 전체 29.22 ms | `schedule`+`compile`+텍스처 ≈ **1.1 ms** |
| 코퍼스 칩 A→B→A (`main.dart:220` `ValueKey('corpus-$selected')`) | prepare 전체 + PNG 재디코드 | **0** — 같은 그림이다 |

두 번째까지 잡으려면 캐시가 필요하다. **캐시는 세 층이다.**

1. **메모리** (같은 화면 안, 슬라이더·칩 왕복) — `PreparedReveal` 을 LRU 2~3장. 단 `RevealPreparer` 는 `const` 값 객체이므로 **상태를 넣으면 그 성질이 깨진다** — 캐시는 앱(조립) 층에 둔다. 그리고 `PreparedReveal` 은 `ui.Image` 를 소유하고 호출부가 `dispose()` 하는 계약이므로, 캐시가 들면 **소유권이 뒤집힌다** — evict 시 `dispose()` 규약과 상한 장수를 명시해야 한다.
2. **디스크** (앱 재실행 너머) — 캐시하는 것은 텍스처가 아니라 `RevealPlan` 의 바이트다(순서맵 w×h + segments). 420 에서 145 KB, PNG 로 접으면 그 이하.
3. **자산** (빌드 시점 — §6.5 사전 굽기).

①→②→③ 으로 갈수록 이득이 크고 규율이 더 든다. **세 층 모두 캐시 키에 `algorithmVersion` 을 넣어야 한다.** 키는 (이미지 쌍, `longSide`, `detectConfig`, `algorithmVersion`) 이고 **timing 은 키가 아니다.** 코어가 바뀌었는데 옛 순서맵을 재생하면 **어떤 테스트도 못 잡는다** — 워킹트리에 있는 `_spread` 체임퍼 변경(길 픽셀의 43% 를 바꾼다)이 바로 그 시나리오다.

⚠️ **이 항목은 전부 추정이다.** 캐시도 분리도 **프로토타입을 만들어 재지 않았고**, 피크 메모리와 `ui.Image` 수명 비용은 부록의 "아직 없는 측정"에 있다. 게다가 인용한 두 호출부가 **모두 `example/` 안**이라, 라이브러리 API 로 올릴지부터 정해야 한다. 이전 판이 이걸 "유일하게 확실한 이득"이라 부른 것은 과했다 — **유일하게 실측이 없는 권고였다.**

### 3순위 — UI 스레드의 약 11.9 ms

굽기를 6.69배 줄여도 이 값은 안 줄고, **프레임을 실제로 막는 것은 이쪽이다.** 후보 셋 **(전부 미측정)**:

- **(가) 디코드를 굽기 해상도로.** 지금은 PNG 를 원본 크기로 통째로 디코드한 뒤(`decodeImageProvider`) `rgbaAt` 이 420 으로 다시 리샘플한다. `ui.instantiateImageCodec(targetWidth:…, targetHeight:…)` 또는 `ResizeImage` 로 처음부터 420 을 받으면 **디코드(5.71)와 리샘플(5.67)이 함께 준다.**
- **(나) 두 장을 겹쳐서.** `prepare()` 의 `rgbaAt` 두 번이 순차 await 다.
- **(다) 사전 축소 자산.**

**(가)는 성능 항목이자 재현성 항목이다** — §5 가 "걷어낼 대상"이라 지목한 `FilterQuality.medium` 엔진 리샘플을 경로에서 없애는 실행안이 이것이다. 단, 코퍼스 상수가 지금 리샘플러의 픽셀로 잰 값이라 **이건 캘리브레이션 변경**이고, `resampler_golden_test.dart` 를 다시 뜨는 것이 조건이다(§840 판정과 같은 대기열).

### 4순위 — 해상도는 최적화가 아니라 **품질 손잡이**다

`RevealPreparer.longSide` 는 이미 생성자 인자이고(`reveal_preparer.dart:69,77`, 주석에 "낮추면 싸지지만 가는 획이 뭉개진다"라고 직접 적혀 있다), `detected.scaleMeasures(kBakeLongSide / longSide)` 가 자 환산까지 해 준다. **코드 0줄로 420 → 210 이 약 4.0배, 420 → 300 이 약 2배**를 돌려준다(굽기 비용이 픽셀 수에 4.0~4.7배로 붙으므로).

이전 판은 해상도를 **올리는** 쪽만 논하고 내리는 쪽은 선택지로 세우지 않았다. 200줄짜리 자료구조 교체(1.80배)와 난독 비트팩(6.69배)을 저울에 올리면서, 그 둘보다 싸고 이미 지원되는 knob 이 저울에 없었다.

여기서 잃는 것은 정확성이 아니라 **가는 갈래의 해상력**이고, 그건 **§저울의 연출 동등성 ①~⑤ 로 잴 수 있는 종류의 손실**이다. 다음에 잴 것: 210·300·420 에서 (ⓐ 뼈대 위상이 갈라지는가 ⓑ `relativeLength` 가 코퍼스 범위를 벗어나는가 ⓒ 눈으로 연출이 달라 보이는가). 셋 다 통과하면 **300 이 비트팩과 같은 급의 이득을 읽히는 코드 0줄로** 준다. 통과 못 하면 그때 비로소 커널 최적화가 필요하다.

곁가지로, "순서 필드만 210 에서 굽고 텍스처는 420 으로 업샘플"도 검토 대상이다 — 순서값은 sharpness 24 의 임계 마스크로 쓰이는 연속 스칼라장이라 보간이 성립할 여지가 있다 **(미측정)**.

### 5순위 — 그래도 커널을 줄여야 한다면, 순서는 이렇다

발동 조건을 먼저 적어 두고 그때까지 잊는다. **(i)** 릴리스 실기기에서 진입→연출 시작 지연이 **이 레포가 정한 UX 예산**(아직 없음)을 초과, 또는 **(ii)** 해상도를 420 아래로 못 내린다고 캘리브레이션이 확정한 경우.

발동하면 순서는:

**ROI 크롭 (위험 0, 바이트 동일, 1.94배, 30줄, 커널 무수정) → ⑧ finish (위험 낮음·불변식 주석 필수, 1.17→0.24) → ⑦ 활성목록 세선화 (위험 낮음, 4.52→0.60) → ⑤ 분리 슬라이딩 형태연산 (읽히는 코드, 8.66→2.84) → ⑥ 비트팩 형태연산 (난독, 퍼즈 테스트 필수, 8.66→0.20)**

①②④ 는 어느 경우에도 넣지 않는다.

⑥⑦⑧ 을 다 넣으면 prepare 는 29.22 → 약 **12.6 ms (추정** — bake 만 교체하고 나머지는 그대로라고 놓은 산술이며, **게다가 컴파일 모드가 섞인 산술이다**: 29.22 와 bake 19.12 는 Flutter DEBUG/JIT, 대입하는 2.21 은 Dart AOT 다. AOT 이득이 약 15% 로 실측됐으므로 남는 약 10.1 ms 도 릴리스에서는 다르게 나온다. **게다가 위 §prepare 표는 부분 합이 총계를 17% 넘는다.** 릴리스 실기기에서 prepare 를 통째로 다시 재기 전에는 **자릿수로만** 읽을 것**)**.

그 시점의 남은 분해는 **AOT 기준으로** thin 0.60 / order 0.59 / spread 0.43 / finish 0.24 / morph 0.20 / threshold 0.10 이라 **지배적인 단일 핫스팟이 사라진다.** 여기서부터는 조각을 줍는 싸움이고, FFI 로 노릴 만한 morph+thin 이 합쳐서 0.8 ms 라 네이티브 경계 비용을 정당화하지 못한다.

### 6순위 (조건부) — 미커밋 `_spread` 체임퍼 변경이 들어올 것인지 확인

워킹트리에 있는 미커밋 수정을 재면 420 에서 +4.20 ms(28%), 840 에서 +16.42 ms(24%)를 더하고 **길 픽셀의 약 43%** 에서 순서값을 바꾼다. 다만 **HEAD 는 c8af051 이고 거기에는 체임퍼가 없다** — 아직 아무것도 회귀시키지 않았고 영영 안 들어올 수도 있다. 들어올 것인지부터 확인하고, 들어온다면 그때 성능·출력 변화가 의도된 것인지 판정한다. **들어오지 않으면 존재하지 않는 문제이므로 순위를 내렸다.**

### 아직 안 물어본 질문 — 이 계산이 꼭 필요한가

bake 의 **85%** 가 "뼈대를 얻는 전처리"(형태 정리 56% + 세선화 29%)다. 기판을 바꾸는 어떤 수보다 큰 이득이 여기 있을 수 있는데 **이번에 안 쟀다.** 우선순위대로:

- **(가) 형태 정리 8패스를 뺄 수 있나.** 존재 이유가 "가장자리 톱니 → 잔가시" 방지인데 잔가시 제거기(`kSpurWidths`)가 이미 하류에 있다. "생략 + 문턱 상향"이 같은 뼈대를 내면 **56% 가 config 한 줄로 사라진다.** 코퍼스 10종에서 뼈대 위상·`length` 를 대조하면 반나절에 답이 난다.
- **(나) Zhang-Suen 대신 Guo-Hall / 한 패스 세선화 / 거리변환 능선.** 반복 수가 줄면 GPU 절의 "수렴 딜레마"도 같이 작아진다. 이름조차 검토된 적이 없다.
- **(다) 뼈대 없이.** 최종 산출물은 "픽셀당 드러나는 시각"이고 뼈대는 중간재다. 길 마스크 위의 측지 거리장(이미 `_spread` 가 0.44 ms 에 하는 그 BFS)만으로 순서 상당 부분이 나온다 — 뼈대가 진짜로 필요한 곳은 되짚기를 처리하는 DFS 한 붓뿐이다.
- **(라) 저해상도에서 세선화하고 뼈대만 업샘플.**

셋 다 출력이 달라지므로 **§저울(연출 동등성 ①~⑤)이 먼저 있어야 판정할 수 있다.**

### 840 에 대한 별도 판정

실측이 "생각해볼 만하다"고 말하는 유일한 지점이지만(AOT bake 69.29 ms, 저사양 6배면 약 420 ms **(추정)**), **이건 성능 결정이 아니다.** 코퍼스 상수(최단 124.5 · 최장 905.7 · 압축 0.35)와 `CrossCalibration` 관문이 전부 420 실측이고 `timing_policy.dart:56` 이 "문구·X 값은 굽기 해상도 420 px 기준"이라고 못 박아 뒀다. `scaleMeasures` 는 자만 환산하지 관문의 유효성을 보장하지 않는다. **840 을 미루는 이유는 느려서가 아니라 캘리브레이션이 없어서다.** 같은 대기열에 §3순위 (가)의 리샘플러 교체가 있다.

### `dart:ffi` — 성능 때문이 아니다

**정정.** 이전 판은 "성능 논거가 없다"고 썼는데 틀렸다. 정확히는 **성능 이득은 있다(같은 알고리즘 기준 morph 구간 1.3~1.8배, 스칼라 전체 3.3~3.7배).** 문제는 **비트팩을 먼저 넣으면 FFI 가 노릴 대상이 morph+thin 0.8 ms 로 줄어 절대 이득이 경계 비용에 못 미친다**는 것이다. 그리고 아래 항목들은 성능과 무관하게 성립한다.

### GPU FragmentProgram — 이득이 음수인데 부채를 진다

**`dart:ui` 는 금칙 목록에 있으므로 코어에 셰이더를 들이는 순간 `purity_test` 가 즉시 막는다.** 셰이더는 `pubspec.yaml` 의 `shaders:` 로 굽는 Flutter 자산이라 `pen_reveal_flutter` 에만 놓을 수 있고, 그러면 **순서 알고리즘의 정본이 층 경계를 넘어 둘로 쪼개진다.**

**그리고 `compute` 를 버려야 한다.** `ui.Picture.toImage`/`toImageSync` 는 엔진 자원이라 background isolate 에서 못 쓴다. isolate 왕복이 이미 무시할 수준인데 그 이점을 내주고 UI 스레드에 GPU 작업을 얹는 거래다.

성능도 진다 — **같은 구간으로 맞춰 대면 420 에서 3.7배, 840 에서 1.7배.** 근본 원인은 왕복이 계산을 압도하는 것이다: **읽기 한 번(0.75 ms) 이 비트팩 CPU 의 형태+세선화 전체(0.80 ms)에 육박한다.** 셰이더가 8비트 RGBA 로 픽셀당 1비트를 나르므로 필요 대역폭의 32배를 쓴다. (단 이 수치는 **워밍업 0회** 프로토콜의 상한값이다.)

**재현성 부채가 특히 나쁘다.** 지금은 엔진 의존이 **스칼라 하나(길이)** 뿐인데, 세선화를 GPU 로 옮기면 **그래프 위상**까지 엔진 의존이 된다. 픽셀 하나가 뒤집히면 뼈대 연결이 갈라지고 → DFS 순서가 바뀌고 → 연출 순서 전체가 바뀐다. 두 백엔드에서 일치한 것은 **12,288 px · 수렴 3라운드짜리 한 케이스**뿐이고, Vulkan·WebGL·`mediump` fp16 기기까지 보증할 방법이 없으며, GLSL 은 Dart 분석기·테스트 커버리지 밖이라 **CI 로 잡을 수도 없다.**

**BFS 전파를 jump flooding 으로 옮기는 것도 마찬가지다.** 파면 라운드 89(최대 129)를 log₂ 9패스로 줄일 수 있지만 대상이 **0.467 ms(2.9%)** 고, JFA 는 근사라 "가장 가까운 뼈대" 소유권이 달라져 순서값이 바뀐다. **단, 이 기각은 바이트 동일 저울 기준이다** — §저울의 연출 동등성으로 재면 다르게 나올 수 있고, 그렇더라도 이득이 2.9% 라 우선순위는 낮다.

**DFS 한 붓 순회의 병렬화는 논할 가치가 없다** — 0.269 ms, bake 의 1.7% 다.

### 플랫폼 채널 — FFI 의 단점을 다 갖고 사본이 하나 더 늘어난다

직렬화가 병목이라는 가설은 실측으로 기각됐지만(145 KB 왕복 ≈0.06 ms), Swift·Kotlin 두 벌 사본 + 웹·데스크톱 부재 + 비동기 배선이 남는다. **FFI 보다 나은 축이 하나도 없다.**

### 런타임 python 세 방식

성능에서 지고(1.5~4.9배 느림), (a)는 오프라인이 죽고, (b)는 iOS 에서 사실상 막히고 앱이 15~40 MB 부는데 import 에만 58.9 ms 를 쓴다. **(c)는 여기서 뺐다** — 기각 사유가 "사전계산"이 아니라 "python 사본"이었기 때문이다. 사전 굽기 자체는 §6.5 로 살렸다.

### 자료구조 교체 ①②④

이득이 각각 −0.12 / +0.06 / +0.07 ms 로 노이즈이고, ① 은 코드가 약 200줄 늘면서 해상도가 올라갈수록 손해가 커진다(840 에서 1.45배). ④ 는 c8af051 기준으로는 대상 코드가 있지만 이득이 노이즈이고, 미커밋 체임퍼가 들어오면 대상 큐 자체가 사라진다 — 어느 쪽이든 넣지 않는다.

### ⑥⑦⑧ 조차, 지금은

6.69배가 공짜처럼 보이지만 정체는 세 최적화의 누적이고, 셋 다 **"이 파일이 순서 알고리즘의 정본이다"라고 선언한 파일을 읽기 어렵게 만든다.** 출력이 바이트 동일한 것과 유지 가능한 것은 다른 문제다. 그리고 그 앞에 **ROI 크롭(1.94배, 커널 무수정)** 과 **해상도 손잡이(약 2~4배, 코드 0줄)** 가 있다. **지금 이 레포의 병목은 CPU 가 아니라 사람이다** — 코퍼스 자산이 없어 대조 테스트가 로컬에서만 돌고, example 데모와 exporter 가 아직 남아 있다.
